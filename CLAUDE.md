# CLAUDE.md

Project memory for Claude Code sessions working in this repository. Updated at the end of each milestone.

## Project shape

`tsdi` is a code-generation TypeScript dependency injection framework. The codegen toolchain is in Rust; the user-facing decorator runtime is a tiny TypeScript package.

Two parallel workspaces share the root:
- **Cargo workspace** — `Cargo.toml` declares `members = ["crates/*"]`.
- **pnpm workspace** — `pnpm-workspace.yaml` declares `packages/*` and `examples/*`.

Both must compile cleanly for CI to pass.

## Crate responsibilities (load-bearing)

| Crate           | Role                                                                                   | Notes                                                       |
| --------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `tsdi-core`     | IR (`Key`, `Binding`, `Provider`, `Scope`, `ModuleDecl`, `ComponentDecl`), graph, validation | No TS knowledge. No I/O. Pure data + rules.                 |
| `tsdi-parser`   | Read TS files via Oxc, extract decorators, build IR                                    | Owns import-map resolution and `Key` minting.               |
| `tsdi-codegen`  | Walk validated IR, emit `*.tsdi.ts` via TS-string → `oxc_parser` → `oxc_codegen`       | Parser validates structure; codegen canonicalizes formatting. |
| `tsdi-cli`      | `tsdi` binary; orchestrates parse → validate → emit; renders diagnostics via `miette`  | Watch mode uses `notify` (M5+).                             |

If a change blurs these boundaries (e.g. teaching `tsdi-core` about Oxc), stop and reconsider — that's a sign the design has drifted.

## Invariants

1. **No runtime reflection.** The runtime `tsdi` package's decorators are no-ops at runtime; all semantics live in the Rust toolchain.
2. **Generated code is plain `.ts`** — never `.js`+`.d.ts`. The user's own `tsc` is the final validator.
3. **Type identity is `(absolute module path, exported name)`**, derived via the file's import map. We do **not** invoke a TypeScript type checker. Non-class deps go through `Token<T>` (deferred to v0.2 / M7).
4. **One generated file per `@Component`**, co-located with the source as `<name>.tsdi.ts`.
5. **TC39 Stage-3 decorators only.** No `experimentalDecorators`. See `docs/adr/0002-stage3-decorators-only.md`.
6. **Apache-2.0 license.** All new code carries this license; no GPL/AGPL deps without explicit user approval.
7. **Oxc, not SWC.** See `docs/adr/0001-oxc-vs-swc.md`. Falling back to SWC requires a new ADR.

## Don't do

- **Don't add the Oxc dependency to `tsdi-core`.** Core is parser-agnostic by design.
- **Don't introduce `reflect-metadata`** anywhere — including in test helpers. The whole point is to avoid it.
- **Don't add `experimentalDecorators` to any `tsconfig.json`.** All sample/test/fixture code is Stage-3.
- **Don't write generated code to disk during unit tests.** Use `insta` snapshots in-memory; reserve disk-touching tests for integration suites under `tests/`.
- **Don't emit unparsed TS.** `tsdi-codegen` builds TS source as a string then runs it through `oxc_parser` + `oxc_codegen` before returning. The parse step is the structural-correctness check (it rejects malformed output before it ever lands on disk); the codegen step canonicalizes formatting. Returning a raw, unparsed string defeats both. Driving `oxc_ast::AstBuilder` directly is also acceptable but not required — the parse-and-print pipeline is the sanctioned default for emission. The banner is the one exception: it's prepended to the codegen output as a comment, since `oxc_codegen` strips comments.
- **Don't shell out to `tsc`** from Rust as a build step. Generated code is validated by the user's tsc; our Rust tests use `assert_cmd` to drive `npx tsc --noEmit` only in fixture-level integration tests.

## Tooling

- Rust: pinned to `1.95.0` via `rust-toolchain.toml` (Oxc 0.127 needs >=1.93). Components: `rustfmt`, `clippy`, `rust-src`.
- Node: `>=20`. Currently used: 24.x.
- pnpm: `10.33.2` (set via `packageManager` in `package.json`).
- Lints: `cargo clippy -- -D warnings`, `cargo fmt --check`, both gating in CI.

## Testing layers (see `CONTRIBUTING.md` for details)

1. Rust unit tests (every crate). Target: `cargo test --workspace` < 5s in M0.
2. `insta` snapshots for IR (M1+), diagnostics (M3+), and emitted TS (M4+).
3. Golden-file fixtures under `tests/fixtures/<case>/{input/, expected/}` (M3+).
4. End-to-end TS validation via `assert_cmd` invoking `npx tsc --noEmit` and `npx vitest run` against fixture output (M4+).
5. Examples-as-tests: every `examples/*` builds in CI on every push (M4+).

## Sibling packages

- **`packages/tsdi`** — runtime decorator stubs (`@Inject`, `@Provides`, `@Module`, `@Component`, `@Singleton`, `@Binds`, `@Subcomponent`, `@IntoSet`). All no-ops at runtime; the Rust toolchain reads decorator presence from the AST. M12 added a method-decorator overload to `@Singleton` so `@Singleton @Provides` typechecks.
- **`packages/tsdi-unplugin`** — bundler integration via [unplugin](https://github.com/unjs/unplugin). One adapter exports per-bundler entry points (`/vite`, `/rollup`, `/webpack`, `/rspack`, `/esbuild`); each plugin runs `tsdi build` on `buildStart` and on debounced filesystem changes, blocking the bundler until codegen finishes so the bundler's TS pipeline picks up fresh `.tsdi.ts` files. Today shells out to the native `tsdi` Rust binary (passed via the `cli` option, defaults to `"tsdi"` on `$PATH`); a future WASM-compiled `tsdi-codegen` would let the package stand alone with no native deps. Tests in `src/index.test.ts` exercise `buildStart` against the real Rust binary in a tempdir fixture (4 tests, all green).

- **M12** — Async `@Provides`. `Provider::ProvidesMethod` gained `is_async: bool`. The parser detects `async` on `@Provides` methods (Oxc's `m.value.r#async`), unwraps the required `Promise<T>` return-type annotation into the inner key via a new `promise_unwrap_to_key` helper (sibling to M9's `ts_type_to_key`), and rejects async-without-Promise with `ExtractError::AsyncProvidesMissingPromise`.   `tsdi-codegen::emit_class_body` was extended with a `graph_is_async: bool` parameter plus a `self_dagger: &str` parameter (the dagger class's name, used for `static async _resolve(d: SelfDagger)`'s parameter type since TS forbids `this` types on static methods). ### M12 gotchas
- The `_resolve` method body is built by **string-rewriting** `this.` → `d.` in each binding's body expression. This works because every dep-call inside a body goes through `this.<getX>()` — closed transform, no other shapes. If a future provider grows a `this.foo.bar` access pattern (or anything that contains `this.` for non-getter purposes), the rewrite would corrupt it. Worth re-examining if the codegen ever changes shape.
- `static async _resolve(d: this)` is **not** valid TS — `this` types aren't allowed on static methods (TS2526). The codegen takes a `self_dagger: &str` parameter and emits the literal class name (`d: DaggerApp`). Two callsites had to change in lockstep when adding the parameter.
- The `Promise<T>` unwrap in `promise_unwrap_to_key` requires the user to write `Promise<…>` literally — TS would *also* accept `async fn(): T` as a valid signature (because `async` implicitly wraps the return), but that loses the explicit "this is async" signal at the type level. Forcing `Promise<T>` keeps the IR's binding key unambiguous and matches what 99% of real code already writes.
- Async `@Provides` is rejected on non-`@Singleton` components (`AsyncBindingNeedsSingletonComponent`) but **not** on `Unscoped` *subcomponents*. The reason: a subcomponent factory is itself per-call (`await dagger.requestComponent(req, res)`), so per-call awaits inside it match the calling pattern. Singleton subcomponents with async bindings work too (`@Singleton @Subcomponent` doesn't conflict with async; only the `@Singleton @Subcomponent` + factory_params combo is rejected by M11).
- The runtime `@Singleton` overload is the *cleanest* place to make `@Singleton @Provides` typecheck — alternatives (separate `@SingletonProvides` decorator, runtime stub typed `any`) are uglier. The implementation is one untyped pass-through `function Singleton(target, _ctx) { return target; }` with two TS overload signatures above it.
- The `dfs` fix from M11 (only push to topo when the key has a local binding) is still load-bearing in M12: the `_resolve` body iterates `topo` and assumes each key indexes into `graph.bindings`. Inherited keys would crash. Same guard, same reason.
- Async `@Inject` ctors aren't reachable from real user code — Oxc's parser rejects them as syntax errors (TS1107). The `ExtractError::AsyncInjectCtor` variant exists as defense-in-depth (in case a future Oxc version loosens the rule), with no test because the path is unreachable today. Don't try to write a test for it; the grammar fails first.
- Mixed-scope graphs are fine: a sync `@Singleton @Inject Foo` whose dep is an async `@Singleton @Provides Bar` works correctly. `_resolve` walks topo, awaits `Bar`, then constructs `Foo` synchronously with the resolved Bar. The codegen detects per-binding async via `binding_is_async(&Key)` rather than treating every binding in an async graph as async.

### M11 gotchas
- The M2 resolver recursing into `EntryPoint.factory_params[i].key` is **not optional** — without it, a factory-param `HttpRequest` Key keeps its raw `./http` specifier (because `from_specifier` seeds `abs` with the specifier) while every other `HttpRequest` Key has the absolute path post-M2. Equality breaks and the child graph thinks `HttpRequest` is missing. Easy to forget to add when extending IR with a new key-bearing field.
- `Provider::FactoryParam` is graph-synthesized like `SetMultibinding` — the parser never produces one. The match arm in `tsdi-parser::symbols::rewrite_binding` exists for completeness but is unreachable today; that's deliberate, future code paths might run rewrites on child graphs.
- Reachability pruning matters semantically, not just for diagnostic noise. Pre-M11 the parent dagger was emitting non-private `getRequestHandler()` factories for `@Inject` classes that semantically belonged to a subcomponent — callers could `dagger.getRequestHandler()` and bypass the subcomponent pattern entirely. The pruning fix forces the architecture to be honored: child-only bindings only exist on the child dagger.
- `dfs` pushing inherited keys to the topo array was a M8-era bug masked by the pre-pruning binding shape. Be wary of any future code that walks a topo and indexes into `bindings`: assume the topo can contain keys without local bindings unless you guard.
- The order of operations in `build_child_graph` matters: factory-param bindings must be inserted *before* the prune step, otherwise the prune walks `Handler.deps = [RequestContext, HttpResponse]` and finds `HttpResponse` neither in bindings nor in any reachable dep chain → drops it. The current order injects, then prunes from entry-point roots, which keeps factory params reachable transitively.
- Adding parameters to a regular `@Component` entry point is rejected at the graph layer, not the parser. The parser doesn't know yet whether an entry point's return type names a subcomponent class — that lookup happens during graph construction. The diagnostic still surfaces at the right span (the entry-point method itself).
- `formal_param_name` returns `Option<&str>` and falls back to a synthetic `_argN` only because destructured / array-pattern parameters can't yield a single field name. v0.1 has no real fixture for this — the synthesized name would compile but is ugly. A future tightening could reject non-identifier patterns at parse time.
- The `SingletonSubcomponentWithFactoryParams` check is a guardrail, not a hard architectural constraint. If a future user genuinely wants singleton-cached results indexed *by request*, they'd need a memoization map keyed on the factory args — that's beyond the dagger's scope.
- The `clippy::too_many_lines` allow on `build_and_validate` is the right call. The function is the orchestration center for the entire validator (aggregate → prune → petgraph → entry-point loop → cycle/scope detection); breaking it apart makes the data-flow harder to follow than it is to read top-to-bottom.

### M10 gotchas
- `ModulePath` is no longer a tuple struct, so `ModulePath(s)` is a parse error and `mp.0` no longer exists. The constructor matrix is now `same_file()`, `from_specifier(s)` (parser-side, seeds both fields), and `from_abs(p)` (test/tooling-side, leaves `original = None`). Every test/fixture that built one as a tuple needs updating — `cargo build` surfaces all sites because the struct definition changed shape.
- **Equality must stay on `abs` only.** Two importers commonly spell the same file differently (`./heater` vs `@/heater` vs `../shared/heater`), and the IR's contract is that those produce equal `Key`s. Deriving `PartialEq`/`Hash` on the new struct would make those compare *unequal* (because `original` differs) and silently break duplicate-binding detection, the SCC-based cycle pass, and the parent-bindings fallback in subcomponents. The custom impl is non-optional.
- The "is this node_modules?" decision is a pure substring match (`abs.contains("node_modules")`). Resilient enough for v0.1 — `oxc_resolver` always lands on a normalized path containing that segment when the resolver crosses a package boundary — but if a project ever has a directory literally named `node_modules` outside a real package install, the heuristic misfires. A future tightening could anchor on a path-component boundary; not worth doing pre-1.0.
- `original` is `Some` for any specifier the parser saw at an `import` statement. It's `None` for `same_file()` and `from_abs()`. Don't unconditionally `.unwrap()` it in codegen — the project-local arm always recomputes, and tooling-built paths should always recompute.
- The parser's `resolve_name_to_key` is the *only* mint site that needs `from_specifier`. Symbol resolution rewrites `abs` in place via `mp.abs = ...`. There's no third path that would silently lose `original`.
- A node_modules import whose `original` is `None` (synthesized by tooling, no parser pass) currently still falls back to relative-path computation — which produces the wrong result. Two options if this ever bites: assert at codegen time, or treat `node_modules + None` as a graph builder bug. Today no codepath produces it, so it's a theoretical hole.

### M9 gotchas
- The element-type lift happens **inside the graph aggregator**, not the parser. The parser emits raw `Binding`s whose `key` is the element type (`Plugin`), with `role: MultibindRole::IntoSet`; the aggregator is what synthesizes `Key::Set { element: Box::new(Plugin) }`. If you try to lift in the parser, every `@IntoSet` binding becomes its own duplicate of `Plugin` (parser sees N contributions producing the same `Key::Class { Plugin }`) and the duplicate-detection rule trips before aggregation runs.
- `Provider::SetMultibinding` is **never** produced by the parser. It's a synthesized provider built only by `aggregate_bindings`. Don't reach for it from the parser side; the round-trip through raw bindings + role is what makes scope-on-the-aggregate work cleanly.
- Each contributor's `deps` are **kept on the contributor**, not merged into a flat list on the binding. The `Binding.deps` field on the synthesized `SetMultibinding` is still the union (so the topo walker visits every contributor's deps before the Set factory), but codegen iterates `contributors` to emit per-contributor `Module.method(args)` calls — they each have their own argument list.
- `Set<T>` parsing required a separate `ts_type_to_key` helper because the existing `type_annotation_to_key` operates on `TSTypeAnnotation`, while a generic argument is a bare `TSType`. Recursing across both shapes inside one function makes the call sites awkward; two functions sharing the recursion is cleaner.
- The factory-naming pair changed from `factory_name(class_name: &str)` (single-string-arg) to `factory_name_for(&Key)` because `Key::Set` has no single class name — there's a wrapper plus an element. The same goes for `cache_field_name` → `cache_field_for(&Key)`. The `class_name_of(&Key) -> &str` helper that returned `&str` was deleted entirely; for `Key::Set`, the type-string is `Set<Plugin>` (a String, not a `&str` slice into the IR), and trying to keep both signatures led to lifetime headaches.
- Adding `Key::Set` is a non-exhaustive break across **every** match on `Key` and **every** `let Key::Class { ... } = ...` destructure: `validate.rs::key_display`, `graph.rs` entry-point matching, `symbols.rs::rewrite_key`, codegen's import-emission and helpers, `cli::explain`'s display, plus 5 places in tests. The `let`-destructure cases are the easy-to-miss ones because rustc's "refutable pattern in irrefutable position" message is less obvious than "non-exhaustive match." Same drill as M7's `Provider::Binds` and M8's `subcomponents` field.
- Adding the `role` field to `Binding` (a non-`Default` field on a non-`Default` struct) breaks **every** `Binding { ... }` literal across the codebase: 3 sites in `tsdi-parser/src/decorators.rs` plus 10 sites across `tsdi-codegen/tests/emit_snapshots.rs`. The graph.rs test helpers needed updating too. Once `MultibindRole: Default` exists, you *could* derive `Default` for `Binding` and use `..Default::default()` to avoid this churn, but the `Default::default()` of `Key`/`Provider` is meaningless so that's not a real option.
- `IntoSet` runtime stubs in test fixtures: every test that writes a fake `tsdi` package needs `export const IntoSet = (..._: any[]) => {};`. Currently only `crates/tsdi-cli/tests/fixtures.rs` was updated (since fixture `06_multibinding_set` exercises `@IntoSet`); other fixtures just don't need it. If you add a new test that uses `@IntoSet`, remember to also add the export to that test's runtime stub.
- The aggregator's pending-contributions map is keyed by the **synthesized** `Key::Set { element }`, not by the raw element key. This was deliberate: keying by `Key::Set` lets the same map handle multiple element types in one component without an extra layer of indirection, and it's what gets directly used as the synthesized binding's key.
- `clippy::derivable_impls` will yell at you if you write `impl Default for MultibindRole { fn default() -> Self { Self::None } }` — use `#[derive(Default)]` plus `#[default]` on the variant instead. Same with `clippy::too_many_arguments` if you push `extract_provides_method` past 7 args (we hit 8 with the new `role` parameter); `#[allow(clippy::too_many_arguments)]` is the right call there since refactoring into a config struct would just be ceremonial.

### M8 gotchas
- A subcomponent is **not** discoverable from a `@Component`'s `modules`. Its only entry path is a parent's abstract zero-arg method whose return type is the `@Subcomponent`-annotated class. The graph builder pattern-matches entry points against `SubcomponentDecl.class` keys; if the parent has *no* such entry point, a `@Subcomponent` is silently unused — that's by design (matches Dagger 2).
- Parent factories called from inside a `Dagger<Sub>` class **must not be `private`** — TS catches this at typecheck time as `error TS2341`. The codegen tracks `parent_keys_exposed = ⋃ child.inherited_keys` and emits those factories without the `private` modifier. Don't try to expose them via a side accessor or a friend class trick — just drop the keyword on the affected factories.
- Inherited deps must route through `this.parent.<getX>()`, **not** be re-built locally with a new factory. The whole point of subcomponents is to inherit the parent's scope cache: a `@Singleton Heater` shared by 100 subcomponent instances must yield 1 `Heater`, not 100. The `dep_call` helper checks `graph.inherited_keys` and emits the parent-routed call when applicable.
- `Binding.deps` for a child binding still names *all* deps (including inherited ones). The graph layer doesn't rewrite `deps` — it uses `parent_bindings` to *silently drop* missing-binding errors during `build_petgraph`, then records the inherited keys separately in `DependencyGraph.inherited_keys`. Codegen consults that set when emitting each call site.
- Adding `subcomponents: &[...]` to `GraphInput` is a non-exhaustive struct break across every callsite: 9 `graph.rs` test cases, the `tsdi-cli` build/check/watch paths, the `tsdi-codegen` emit signature, and 5 codegen tests. There is no central registry — `cargo build` is what surfaces them. Same drill as M7's `Provider::Binds` arm.
- The `tsdi` runtime stubs in `crates/tsdi-cli/tests/fixtures.rs` (and friends) need `export const Subcomponent = (..._: any[]) => {};` added when fixtures use `@Subcomponent`. Forgetting this surfaces as `oxc_resolver` errors during `parse_file`, not as a TS error — confusing.
- Subcomponent classes are emitted in the **same** `.tsdi.ts` file as their parent. There's no separate `request-component.tsdi.ts`. This was deliberate: subcomponents have no standalone factory, so a separate file with no `create*` export would be confusing.
- A subcomponent's own `ComponentDecl`-shaped fields (`modules`, `scope`, etc.) are recognised, but custom scope tags beyond `Singleton`/`Unscoped` are not. M9+ will tackle scope-tag annotations.

- **M7** — `@Binds` interface aliasing landed (scoped to `@Binds` only; `Token<T>` deferred). `Provider::Binds { target: Key }` was added to `tsdi-core::ir`; the parser dispatches `@Provides`/`@Binds` to `extract_provides_method`/`extract_binds_method` and emits `Binding { provider: Binds { target }, deps: vec![target.clone()], .. }` so the topo walker visits the implementation before the alias factory references it. `@Binds` methods must be **`static`** with a single parameter and an explicit return type; TC39 Stage-3 decorators cannot decorate abstract methods (TS error 1249), so the user writes a static method with a trivial body (`return impl;`) — `tsdi-codegen` ignores the body and emits `return this.<getTarget>()` for the alias factory. `Singleton` semantics are unchanged: scope is per-binding, so the target's binding owns the cache. New parser errors `BindsNotStatic`, `BindsMissingReturnType`, `BindsWrongArity`, `BindsAndProvides`. The runtime `tsdi` package gained a `Binds` no-op decorator stub (matches `Provides`'s shape). Tests: 4 new parser tests (1 snapshot + 3 error variants) in `crates/tsdi-parser/tests/extract_snapshots.rs`, 1 codegen snapshot `emit_binds_alias_delegates_to_target` in `crates/tsdi-codegen/tests/emit_snapshots.rs`, and golden-file fixture `tests/fixtures/04_binds/{input,expected}` (abstract `Heater` ← `ElectricHeater` via `HeaterModule.bindHeater`) plus `fixture_04_binds` in `crates/tsdi-cli/tests/fixtures.rs`.

### M7 gotchas
- TC39 Stage-3 decorators **cannot** decorate abstract methods (Oxc parses but flags TS error 1249). The Dagger 2 `@Binds abstract` shape is therefore unavailable in TS Stage-3. We instead require `static` `@Binds` methods with a trivial `return impl;` body — `tsdi-codegen` ignores the body and emits `return this.<getTarget>()`. The body still has to type-check so the user's `tsc` accepts the source file.
- `Binding.deps` for a `Provider::Binds { target }` **must** be `vec![target.clone()]`. The topo walker uses `deps` to order factory emission; without target in `deps`, the alias factory could be emitted before the implementation factory and reference an undefined `getX()`.
- The Binds factory body never calls `new` — it forwards to `this.getTarget()`. Don't be tempted to inline `new Target(...)` "for clarity": the indirection is what makes scope (Singleton caching, etc.) work transparently — the target's binding owns its own factory and cache.
- Adding `Provider::Binds` is a non-exhaustive match break across the codebase. Every `match` on `Provider` in `tsdi-core::graph`, `tsdi-codegen::emit_component`, `tsdi-parser::symbols::rewrite_binding`, and `tsdi-cli::explain::provider_label` needs an arm. There's no central registry — `cargo build` is what surfaces them.
- `extract_provides` now dispatches to `extract_provides_method`/`extract_binds_method` based on which decorator is present. Methods may not have **both** `@Binds` and `@Provides`; `BindsAndProvides` rejects that combination loudly (the alternative — silently picking one — would be a footgun if the user adds the second decorator and expects different semantics).
- Test stubs for the `tsdi` runtime package (the inline `pkg/index.ts` written by `crates/tsdi-cli/tests/*.rs` and `crates/tsdi-parser/tests/symbols_resolution.rs`) all need `export const Binds = (..._: any[]) => {};` added when adding new decorators — there's no shared helper. Easy to miss when copying patterns.

### M6 gotchas
- The `??=` (logical-nullish-assignment) operator returns the assigned value, so `return this._x ??= <expr>` is correct — it lazily initializes on first call and returns the cached value on every subsequent call. Don't second-guess it into a 3-line `if (x === undefined) ...; return x` block; the operator is exactly the right primitive.
- The cache field type **must** be `T | undefined` (not bare `T`). With `strictPropertyInitialization` users will compile-error on the bare form because the field has no initializer in the dagger constructor. `T | undefined` makes it explicitly optional.
- Field names use a leading underscore + lowerCamel of the class name (`Heater` → `_heater`, `HotPump` → `_hotPump`). Lowercasing only the first character is what TS convention expects; using the full lowercase (`_heater`) for `HotPump` would lose the camel-hump.
- Topo-order matters for the cache-field block too: declaring `_heater` before `_pump` (when both are singletons) keeps the field block in the same order users see the factories — easier to scan when debugging the generated file.
- Unscoped bindings that *depend* on singleton bindings are still unscoped — `Pump` calls `this.getHeater()`, which routes through the cache. This is the intended Dagger semantics: scope is a property of the binding, not the call site.
- Removing `EmitError::SingletonNotYetSupported` is a breaking change to `tsdi-codegen`'s public error enum. Pre-1.0, fine; just be aware that downstream `match` arms will need updating.

### M5 gotchas
- `notify::RecommendedWatcher::new(tx, Config::default())` creates a non-debounced watcher — editor saves emit a flurry of events. The 100ms `recv_timeout` debounce in the inner loop is required, not optional. Without it a single save triggers 3–10 rebuilds.
- Watch events surface OS-native paths; `std::fs::canonicalize` them on receipt so they compare equal to the canonical paths stored in each entry's source closure (the closure paths come from `ProjectGraph` which canonicalizes via `oxc_resolver`). On Windows `canonicalize` adds `\\?\` UNC prefixes, but both sides go through the same call so equality still holds.
- Long-running subprocess tests need a deterministic exit. The `TSDI_WATCH_ITERATIONS` env-var bounds the loop iteration count; `crates/tsdi-cli/tests/watch_command.rs` polls `child.try_wait()` with a deadline rather than blocking on `wait()` so a hung test still fails instead of stalling CI forever.
- `clap`'s `conflicts_with = "config"` on the `entry` field is the right way to express mutually-exclusive flags inside an `Args` group — don't roll your own check in `main`.
- `glob::glob` patterns are interpreted as platform-native paths but `**/` works on both Windows and Unix. Anchor patterns at `root_dir` (an absolute, canonicalized path) and let glob handle the cross-platform separator concerns.
- `serde(deny_unknown_fields)` on `RawConfig` is deliberate — typos in `tsconfg` or `outputSufix` should fail loudly rather than silently revert to defaults.
- The `output_suffix` and `source` fields on `Config` are loaded but unused end-to-end yet (output_suffix becomes load-bearing in M6 once we re-thread it through the emitter); annotate them with `#[allow(dead_code)]` instead of deleting — removing them just to re-add them next milestone is churn.

### M4 gotchas
- `oxc_codegen::Codegen::build` strips comments from the printed AST. The banner and `// Source:` lines must be **prepended** to the codegen output as text — they cannot be embedded into the parsed program.
- `@Inject` is a **class-level** decorator, not a constructor decorator. TC39 Stage-3 decorators don't apply to constructors. The parser rejects the legacy `@Inject constructor(...)` placement with `ExtractError::InjectOnConstructor`. When `@Inject` sits on the class, the parser still walks the `constructor` method's parameter types to populate `Provider::InjectCtor.deps`. The emitted `.tsdi.ts` is decorator-free regardless.
- Computing relative paths via `std::path::Path::components` requires both inputs to be absolute, which they are post-M2 — but on Windows the components include a `Prefix(C:)` and `RootDir`, so the simple "common-prefix length" comparison still works. Tests use `tempfile::TempDir` paths so they're truly absolute on both OSes.
- `assert_cmd::Command::cargo_bin("tsdi")` rebuilds the binary on every test invocation — keep the binary's compile time low (no heavy `dev-dependencies` linked into the bin) or test runs balloon.
- Golden-file fixture tests use a `BLESS=1` env-var convention rather than `insta`'s `--review` workflow because the fixture lives outside the snapshot-managed directory tree (it's a deliberate on-disk artifact, not an internal test detail).

### M3 gotchas
- `petgraph::graphmap::DiGraphMap` requires `Ord` keys; `Key` is only `Hash + Eq`. Use `DiGraph<Key, ()>` + a `HashMap<Key, NodeIndex>` lookup instead.
- A SCC of size 1 is *not* a cycle unless `graph.contains_edge(ix, ix)`. Without that check Tarjan reports every node as cycling.
- `miette::MietteDiagnostic::with_labels` attaches `LabeledSpan`s relative to a single `NamedSource` (set via `Report::with_source_code`). For multi-file diagnostics, embed cross-file labels in the `help` string instead of adding `LabeledSpan`s pointing into the wrong source.
- Adding `source: SourceSpan` to IR types invalidates every M1 IR snapshot. Re-accept with `INSTA_UPDATE=always cargo test -p tsdi-parser`.
- `predicates::str::contains(...).and(...)` requires `use predicates::prelude::PredicateBooleanExt;`.
- `clippy::too_many_lines` defaults to 100; the validator entry point exceeded that. Split into `aggregate_bindings` / `build_petgraph` / `detect_cycles` / `detect_scope_mismatches` instead of an `#[allow]`.

### M1 gotchas
- Oxc 0.127's `FormalParameter` has `type_annotation` directly on the parameter — **not** on `pattern` (`pattern` is a `BindingPattern` enum with no fields).
- Oxc abstract methods are `MethodDefinition` with `r#type == MethodDefinitionType::TSAbstractMethodDefinition` (and `kind == Method`). Distinguishing abstract vs concrete via `kind` alone is wrong.
- `oxc_ast::ast::TSTypeName::IdentifierReference` is what a bare `T` in a type annotation looks like; member-expression types (`ns.T`) are not in scope for v0.1.
- Side-effect-only imports (`import "./register"`) have `decl.specifiers == None` — handle that explicitly when building the import map.

### M2 gotchas
- `oxc_resolver::Resolver::resolve` takes the **directory** of the importing file (not the file itself). Passing the file path silently returns confusing results.
- The default `extensions` list does *not* include `.ts`/`.tsx`. If you forget to set them, every `import "./foo"` fails. Order matters too: list `.ts` before `.js` so source wins over emitted output.
- `Resolution::full_path()` returns a `PathBuf`. `path()` returns a `&Path`. Both are absolute but use the OS-native canonical form on Windows (UNC `\\?\` prefixes from `fs::canonicalize` are normalized away by `oxc_resolver`).
- Barrel re-exports (`export { X } from "./y"`) resolve to the barrel file, **not** to the underlying declaration. M3's binding-graph walker is the layer that follows re-exports — the M2 resolver only normalizes specifier→absolute-path, it does not chase declarations.
- `tsconfig.json` `paths` only takes effect when `ResolveOptions::tsconfig` is `Some(TsconfigDiscovery::Manual { config_file, .. })` — there's no auto-discovery from arbitrary cwds.
